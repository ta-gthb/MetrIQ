# OIML R 76 coverage and rules matrix

Generated from the versioned rule data, the test catalogue and the registered calculators. Regenerate with:

```powershell
cd backend
python -m scripts.build_coverage_matrix
```

| Standard | OIML R 76-1 |
| Edition | 2006 |
| Ruleset version | `r76-1-2006-v1` |
| Report template | `r76-2-2007-v1` (OIML R 76-2) |
| Activation | Inactive after deployment; only a System Administrator can activate or deactivate it. |
| Rule source | Definitions and clause references are versioned with this ruleset. The numeric boundary cases that back each rule live in `tests/test_rule_boundaries.py`. |

The matrix is versioned with the ruleset: a new standard version produces a new set of rows, and historical cases stay bound to the version they were evaluated against.

## 4. Report section provenance

Answers the audit question *is any report field populated by an unexplained or manually typed result?* Every section of `r76-2-2007-v1` names the records it is built from.

| Section | No. | Title | Required | Populated by | Sourced from |
| --- | --- | --- | --- | --- | --- |
| `cover` | 0 | Cover page and report identification | yes | `config.settings` + `evaluation_cases` | Deployment settings (`REPORT_LABORATORY_NAME/CODE`) and the case title and purpose; not typed at report time. |
| `applicant` | 1 | Applicant and manufacturer | yes | `applicants` via `evaluation_cases.applicant_id` | Master record attached to the case. |
| `instrument` | 2 | Instrument identification and metrological characteristics | yes | `instruments` + `instrument_ranges` | Instrument record with its range/interval table; the scale intervals the engine used are the values shown here. |
| `conditions` | 3 | Laboratory and test conditions | yes | `environmental_conditions` | Rows recorded against the case during the evaluation. |
| `equipment` | 4 | Test equipment and traceability | yes | `test_equipment_usage` + `test_equipment` | Only equipment linked to the case, with its calibration record. |
| `summary` | 5 | Summary of applicable tests and results | yes | `metrology_service.summarise_case` | Derived from `test_instances.result_status`; never typed by an operator. |
| `tests` | 6 | Individual test records | yes | `test_instances` + `calculation_runs` + `compliance_results` | One block per catalogue entry, using the row detail the deterministic engine stored. |
| `checklist` | 7 | Construction and identification checklist | no | `test_instances` for the T-CHK-* definitions | Checklist decisions recorded as observations; the aggregate status is computed by the checklist calculator. |
| `evidence` | 8 | Evidence and attachments | no | `attachments` | Index of uploaded files with their SHA-256 digests. |
| `review` | 9 | Review, approval and signatures | yes | `evaluation_cases` (+ `workflow_actions`) | Named engineer, reviewer and approver with the workflow timestamps. Approval and hashing only: no digital signature is claimed. |
| `versions` | 10 | Ruleset, template and revision history | yes | `standard_versions`, `rule_versions`, `report_template_versions` | The exact ruleset and template the case was evaluated against, plus the case revision number. |
| `verification` | 11 | Document verification | no | `meta.content_hash` / `meta.verification_code` | SHA-256 over the canonical snapshot; recomputable by anyone holding the report data. |
